A **plugin** is how an agent gets to do something. It's a plain object that tells Mercury its name, a few lines
for the model about what it offers, and the **tools** it contributes: functions the model can decide to call, with
a description of what they do and of the input they take.

This page writes one inside your app, the guest Wi-Fi plugin from [Your first agent](../first-agent/). A plugin
living in your app is for your app only; to share one with every Mercury user, see
[Proposing a plugin](../public-plugin/). What every kind of plugin looks like, and the rules they all follow, is in
[Writing a plugin](../../concepts/writing-plugins/).

## Create it

From the app's folder:

```bash
bunx mfw plugin create tool guest-wifi
```

```text
Wrote plugins/guest-wifi (@my-agent/plugin-guest-wifi), a tool plugin.
Declared it in package.json and in mercury.config.ts.
Next: its settings (plugins/guest-wifi/README.md), bun run test, then mfw restart.
```

`tool` is the kind of plugin (one with tools the model calls; `bunx mfw plugin create --help` lists the others), and
`guest-wifi` its name. The command wrote a package of the app's own in `plugins/guest-wifi`, a working example with
its tests, and did three more things:

- it added the package to the app's `package.json`, as `"@my-agent/plugin-guest-wifi": "workspace:*"`: the app
  installs it from its own folder, not from npm (`my-agent` is your app's name);
- it declared it in `mercury.config.ts`, with an import and `guestWifiPlugin()` at the end of `plugins`;
- it ran `bun install`, to link it.

The example lists the items of a service and deletes one after the person confirms, with a skill telling the model
how. The Wi-Fi needs much less, so the next step makes it smaller.

## Make it the guest Wi-Fi

Delete what the Wi-Fi doesn't need, the example's tools and its skill:

```bash
rm plugins/guest-wifi/tools.ts plugins/guest-wifi/tools.test.ts
rm -r plugins/guest-wifi/skills
```

Then replace `index.ts`:

```ts title="plugins/guest-wifi/index.ts"
/**
 * The guest Wi-Fi plugin: tells people the name and password of the office
 * guest Wi-Fi, from the app's settings.
 */
import type { Plugin } from "@mercury-fw/kit";
import { tool } from "ai";
import { z } from "zod";
import { GUEST_WIFI_MESSAGES } from "./messages.ts";

/** The plugin. */
export function guestWifiPlugin(): Plugin {
  return {
    // The contract this plugin is written for, as a literal: importing
    // PLUGIN_API_VERSION would report whichever contract is installed.
    apiVersion: 7,
    name: "guest-wifi",
    description: "Tells people the name and password of the office guest Wi-Fi.",
    actsAs: "anyone",
    systemPromptFragment:
      "## Guest Wi-Fi\n{{assistant}} can look up the office guest Wi-Fi with `guest_wifi`. Use it when someone asks how to get online.",
    messages: GUEST_WIFI_MESSAGES,
    build: (ctx) => {
      const network = ctx.env.GUEST_WIFI_NAME;
      const password = ctx.env.GUEST_WIFI_PASSWORD;
      if (!network || !password) {
        ctx.log("guest-wifi: GUEST_WIFI_NAME or GUEST_WIFI_PASSWORD is not set: no tools");
        return {};
      }
      return {
        sessionTools: () => ({
          guest_wifi: tool({
            description: "Returns the name and password of the office guest Wi-Fi.",
            inputSchema: z.object({}),
            execute: async () => ({ ok: true, network, password }),
          }),
        }),
        toolStatusDescribers: {
          guest_wifi: (_input, t) => t("guest-wifi.status.lookup"),
        },
      };
    },
  };
}
```

Field by field:

- **`apiVersion`** is the version of the contract the plugin was written for. Mercury checks it when it loads the
  plugin and skips one it can't run, saying why in the log, instead of failing later in a stranger way. It's a
  number written out, not the `PLUGIN_API_VERSION` constant: the constant says which contract is installed, not
  which one this code was written for.
- **`name`** is what the logs call the plugin, and how its texts' keys start.
- **`description`** says, in one sentence, what the plugin lets the agent do. The model reads it before every
  conversation, next to the other plugins' ones, and answers from that list when someone asks what it can do. It's
  required: Mercury skips a plugin without one, saying why in the log.
- **`actsAs`** says whose identity the tools use at the service they reach. `"anyone"` means none: there's no
  login, and everyone may use it. [People and roles](../../concepts/people/) explains the other two.
- **`systemPromptFragment`** goes into the instructions the model reads before every conversation, so it knows the
  tool exists and when to use it. `{{assistant}}` becomes the assistant's name.
- **`messages`** are the texts the plugin shows the person, in English, every key starting with its name.
- **`build`** runs once at startup, with the environment in `ctx.env`. It reads the two settings and, when one is
  missing, logs it and contributes nothing: the agent starts anyway, without the tool. That's how every plugin
  behaves, so one plugin set up wrong never stops the rest.
- **`sessionTools`** returns the tools by name. `description` is what the model reads to decide whether to call
  it, `inputSchema` the input it must send (none here), and `execute` what runs. What `execute` returns goes back to
  the model, which writes the answer from it.
- **`toolStatusDescribers`** give the line the person sees while a tool runs, one of the plugin's `messages`.

`build` may also be `async`, for a plugin with something to set up before the agent takes messages. What else it
can reach besides `ctx.env` (the models, the vector index, work at a set time) is in
[What a plugin can use](../../concepts/primitives/).

The status line's text goes in `messages.ts`, replacing the example's:

```ts title="plugins/guest-wifi/messages.ts"
/**
 * The plugin's texts a person sees, in English: the status line while its
 * tool runs. The app's language files translate them.
 */
import type { Messages } from "@mercury-fw/kit";

export const GUEST_WIFI_MESSAGES: Messages = {
  "guest-wifi.status.lookup": "Looking up the guest Wi-Fi",
};
```

## Its tests

The tests go next to the plugin, replacing the example's `index.test.ts`:

```ts title="plugins/guest-wifi/index.test.ts"
import { describe, expect, test } from "bun:test";
import type { PluginRuntimeContext, SessionToolContext } from "@mercury-fw/kit";
import { guestWifiPlugin } from "./index.ts";

/** The context Mercury builds a plugin with: this plugin reads only `env` and `log`. */
function ctx(env: Record<string, string>, logs: string[] = []): PluginRuntimeContext {
  return { model: {} as never, env, log: (line) => logs.push(line) };
}

const SETTINGS = { GUEST_WIFI_NAME: "Office-Guest", GUEST_WIFI_PASSWORD: "secret" };

describe("guest-wifi", () => {
  test("without its settings it contributes no tool, and logs why", async () => {
    const logs: string[] = [];
    expect(await guestWifiPlugin().build!(ctx({}, logs))).toEqual({});
    expect(logs).toEqual(["guest-wifi: GUEST_WIFI_NAME or GUEST_WIFI_PASSWORD is not set: no tools"]);
  });

  test("guest_wifi returns the network and the password from its settings", async () => {
    const built = await guestWifiPlugin().build!(ctx(SETTINGS));
    const tools = built.sessionTools!({} as SessionToolContext);
    expect(await tools.guest_wifi!.execute!({}, {} as never)).toEqual({ ok: true, network: "Office-Guest", password: "secret" });
  });

  test("its status line is one of its texts", async () => {
    const plugin = guestWifiPlugin();
    const built = await plugin.build!(ctx(SETTINGS));
    expect(built.toolStatusDescribers?.guest_wifi?.({}, (key) => plugin.messages?.[key] ?? key)).toBe("Looking up the guest Wi-Fi");
  });
});
```

The app's `bun run test` runs them with every other plugin's, and `bun run typecheck` checks the types:

```bash
bun test plugins/guest-wifi
```

```text
 3 pass
 0 fail
 4 expect() calls
Ran 3 tests across 1 file.
```

## Its settings

The password is a secret, so it goes in `.env` and nowhere else:

```bash title=".env"
GUEST_WIFI_NAME=Office-Guest
GUEST_WIFI_PASSWORD=correct-horse-battery
```

Add the two names to `.env.example` too, with no values, so whoever sets the app up next knows they exist. Then
restart, so the image picks up the plugin and the container the settings:

```bash
bunx mfw restart
```

[Step 6 of Your first agent](../first-agent/#6-check-it-uses-the-tool) shows what comes back when you ask about the
Wi-Fi.

## The smallest plugin: one file

A plugin doesn't have to be a package. The same object can live in a single file under `src/` (the folder the app's
image copies), say `src/plugins/guest-wifi.ts`, imported by `mercury.config.ts` from there
(`import { guestWifiPlugin } from "./src/plugins/guest-wifi.ts";`), with `@mercury-fw/kit`, `ai` and `zod` added to
the app itself (`bun add @mercury-fw/kit ai zod`). It's quicker for a plugin of a few lines; a package keeps its
tests, its texts and its own dependencies apart, and is the shape a plugin needs to be published one day.
