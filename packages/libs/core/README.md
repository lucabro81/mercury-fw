# @mercury-fw/core

The runtime of [Mercury](https://github.com/lucabro81/mercury-fw): it builds an agent from the config an app gives it and runs it, from the conversation loop to the channels. An app depends on it; a plugin doesn't (plugins build on [`@mercury-fw/kit`](https://www.npmjs.com/package/@mercury-fw/kit)).

On Mercury's documentation site: [What Mercury is](https://lucabro81.github.io/mercury-fw/concepts/what-mercury-is/).

The usual way to get it is scaffolding an app, which wires it up for you:

```bash
bun create mercury-agent my-agent
```

## What it exports

- `defineMercuryConfig(config)` types the app's `mercury.config.ts`: `plugins`, `channels`, `auth` (the provider that tells a channel like HTTP who is calling, or a list of them tried in order, the first that recognizes the caller deciding; each provider's people are its own, so the same person coming in through two providers is two people; HTTP doesn't start without one), `directory` (who that is to Mercury, with their roles; a closed instance for anyone it doesn't know), `vectorIndex` (where the memory is found by meaning: the episodic memory, the semantic facts, the procedural corrections and `recall_verbatim`'s search; without one none of them runs, and idle conversations close without a summary), `conversationStore` (where every conversation is kept word for word, with its title: without one nothing is archived, no conversation is reopened or listed, the HTTP channel serves no conversation routes, and there's no `recall_verbatim`), `access` (whether unknown people are let in, and which roles a plugin is restricted to), `i18n` (the instance's language files, `defaultLocale` and `timeZone`, see [Languages](https://github.com/lucabro81/mercury-fw/blob/main/apps/docs/src/content/docs/concepts/languages.md)), `models` (the models it runs on, by role: `turn`, required, for the turns, the compression summary and plugins' checks; `background`, the turn's when left out, for titles, memory captures, corrections and the nightly review; `embedding`, needed with `vectorIndex`, which stops the start without one; see [the config reference](https://github.com/lucabro81/mercury-fw/blob/main/apps/docs/src/content/docs/reference/config.md#models)), `persona`, `traces` (where the events of what the agent does go and how much they carry, `meta` by default or `args`; nothing is recorded without it, see [Traces](https://github.com/lucabro81/mercury-fw/blob/main/apps/docs/src/content/docs/concepts/traces.md)), `version` (the app's own version, its `package.json`'s, handed to channels as `ctx.appVersion` and shown on the HTTP channel's `GET /version`, see [the config reference](https://github.com/lucabro81/mercury-fw/blob/main/apps/docs/src/content/docs/reference/config.md#version)).
- `composeMercury(config)` builds the agent from that config and the environment, and returns what the entrypoints start: `handleTurn`, the declared channels with their runtime, the background jobs (`startCrons`), the `tracer` the events go through (the service hands it to `loadChannels` and flushes it on shutdown), and `texts`, the texts a person sees in their language, which the REPL entrypoint hands to `createTerminalProvider({ texts })` for the terminal's own lines.
- `loadChannels(channels, { runtime, tracer? })` turns the declared channels into started providers, recording which started and which were left out, and why, when given the app's `tracer`; and `createTerminalProvider(...)` opens the dev REPL on `handleTurn`.
- The types `MercuryI18n` (the config's `i18n`), `Messages` (a language file's texts, key to text), `Texts` and `Translate` (the texts for a person, and the function giving one by key); `Messages` and `Translate` are the plugin contract's (`@mercury-fw/plugin-types`), re-exported.
- `envNumber(name, fallback?)` and `envBoolean(name, fallback)` read a config field's value from an environment variable: a number, or `true`/`false`; empty or unset gives the fallback, anything else throws naming the variable. A scaffolded app's turn model reads `OLLAMA_THINK`, `OLLAMA_TEMPERATURE`, `OLLAMA_TOP_P`, `OLLAMA_TOP_K`, `OLLAMA_CAPACITY` and `OLLAMA_BACKGROUND_SLOTS` with them.
- `ollamaModel(name, settings?)` declares a model on the instance's Ollama: its name there, how it generates (`think`, `temperature`, `topP`, `topK`; a field left out isn't sent, so the model's own value applies), `capacity`, how many requests its server answers at once (1 when left out), and `backgroundSlots`, how many of them the work nobody waits on may take (1 when left out, below a capacity above 1, only 1 with capacity 1). `ollamaEmbedding(name, { capacity }?)` declares an embedding model. Both return a handle, given to the roles in `models` or to a plugin's own configuration (the plugin gets the model with `ctx.modelFor`); an empty name or a value out of its range throws, so a wrong config stops the start.
- `pseudonymOf(secret, key)` is the pseudonym a person's key or a session key gets in the traces, to find one person's events with the secret in `trace-secret` in the data folder; the types `MercuryTraces`, `TraceLevel` and `Tracer` go with it.
- `DEFAULT_PERSONA_IDENTITY`, `DEFAULT_PERSONA_TONE` are the persona an app gets when its config sets none, both referring to the assistant's name as `{{assistant}}`.
- `assistantNameOf(persona)` is the assistant's name (`persona.name`, Mercury by default), refusing one that can't stand in a prompt: blank, longer than 40 characters, on more than one line. `composeMercury` refuses to start on such a name.

A scaffolded app's `src/index.ts` (the service) and `src/repl.ts` (the REPL) are the reference for using them.

## Environment

| Variable | |
|---|---|
| `OLLAMA_HOST` | The Ollama-compatible endpoint. Required. |
| `WIKI_VAULT_PATH` | Where the wiki lives. Required. |
| `MERCURY_DATA_PATH` | Where Mercury keeps its own state, on a volume of its own: account links, profiles, the plugins' data, traces and their secret. Required. On the first start with an empty folder, what an older instance kept in the vault's `.mercury/` is copied here; the original is left where it is. |
| `TURN_STALL_TIMEOUT_MS` | How long a turn on a streaming channel (the HTTP surface) waits for the model's next token or step before it's stopped with an error, "the model sent nothing for N seconds" (default 120000, two minutes; `0` turns it off). A tool that takes long doesn't count: the wait pauses while a tool runs. Without it, a model server that stops sending mid-answer leaves the turn, and its conversation, hanging until the service restarts. |

A conversation store or a vector index that can't be reached degrades memory, it doesn't stop the agent. Where they connect is their own packages' business (`@mercury-fw/store-qdrant` reads `QDRANT_URL`).

Which models the instance runs on isn't read from the environment by the core: it's the config's `models`, which a scaffolded app declares from `OLLAMA_MODEL` and `OLLAMA_EMBEDDING_MODEL`, and the turn model's settings from `OLLAMA_THINK`, `OLLAMA_TEMPERATURE`, `OLLAMA_TOP_P`, `OLLAMA_TOP_K`, `OLLAMA_CAPACITY` and `OLLAMA_BACKGROUND_SLOTS`. The embedding model's vectors' length sizes the vector index's spaces. The startup log says what each role runs on (`[model] turn qwen3.8:27b: think on, temperature 0.2, capacity 1`).

## How Mercury remembers a conversation

A language model remembers nothing between one answer and the next. Every time it answers, it gets the whole conversation again as text, from the first message to the last, and reads it from scratch. That text has a size limit, the model's context window, so a long conversation can't be handed over forever as it is.

Mercury keeps four things for every conversation ([Memory](https://lucabro81.github.io/mercury-fw/concepts/memory/) on the documentation site explains them for someone new to it):

- **the history**, the conversation as the model gets it, kept in memory while the conversation is active;
- **its summary**: when the history grows past about 60,000 characters, its older part is replaced by a summary written by the model, and the conversation goes on from the summary plus the recent messages (this is called compaction);
- **the archive**, every message word for word, kept in the conversation store the config declares (`conversationStore`) and never summarized: it's what a UI shows when it reopens a conversation, and what the model can search when it needs an exact quote; next to it, each conversation's **title**, which the model writes after the first message the person sends (again after the next one if it couldn't) and the person can change; a title the person chose is never replaced, and without the model the conversation just has none;
- **the long-term memory**: short summaries of what was said, asked and decided (never the data a tool returned, which changes), which Mercury uses in later conversations to remember the person.

The history lives in the process's memory, so Mercury frees it once a conversation has been quiet for a while (`SESSION_IDLE_TIMEOUT_MS`, 30 minutes by default). Before freeing it, it writes its summary to the long-term memory.

What happens next depends on the channel:

- **On a channel with a single stream of messages**, like a Google Chat space, a quiet stretch closes the conversation. The next message starts a new one, and the model gets a recap of the last one as background: possibly out of date, to bring up only if the person refers to it, never as its own words.
- **On a channel where one person keeps many conversations and reopens them whenever they want**, like the HTTP surface behind a web chat, a new conversation is a deliberate fresh start and nothing from another one comes in, unless the person asks (the model can search the archive then). A conversation never ends, though. Freeing the history only empties a cache: the next message rebuilds it from the archive, as a compaction would, with the summaries of the older part and the newest messages word for word. To the model, and to the person, it's the conversation that was on screen. Whatever comes back is already in the long-term memory, so only the new messages go there.

| Variable | |
|---|---|
| `SESSION_IDLE_TIMEOUT_MS` | How long a quiet conversation keeps its history in memory (default 30 minutes). Lower it to free memory sooner. A reopened conversation on HTTP doesn't notice. |
| `SESSION_RESUME_MAX_CHARS` | How many characters of a reopened conversation come back to the model (default 30,000). Raise it to give the model more of the past, at the cost of a longer prompt on every answer, which a small model or slow hardware pays for. `0` turns resuming off where the channel doesn't set its own. |
| `HTTP_SURFACE_RESUME_MAX_CHARS` | The same, for the HTTP surface only; see [its README](../../channels/channel-http/README.md). |

What the history keeps of an answer is its text and the tool calls it was written from. Of each call it keeps what it ran and how it went (whether it worked, how many items it found, the list it built, the error), never what it returned: on later turns the model gets these calls back as its own, so it sees that it looked things up, and it's told to run the tool again when it needs the data. For a skill it read, the history keeps the call, not the skill's text, and the model is told to read the skill again before using its tools. A conversation reopened over HTTP brings them back too, from the archive. The reads that show a conversation leave them out; the raw reads of the archive (`GET /memory/scroll`, `mfw memory read verbatim_archive`) show them as a `calls` field, next to `displays`. A list the answer showed (the lists a plugin's tools hand over, which the model shows with `present`, or which the instance's formatter rule shows always) isn't in it, so the model is told at the end of every prompt which lists it already showed in the conversation: a short ref and the tool and input that built each one, never the list itself. It can show one again by its ref, or call the tool again for fresh data. The model never reads a list: the core takes the `display` out of every plugin tool's result and keeps it under that ref, and what a turn that failed or was stopped marked to show is dropped, never appended to the next answer. These refs live as long as the conversation's history, at most ten per conversation. Of a turn stopped while the model was answering (the person stopped it, or the HTTP client closed the connection), the history keeps the person's message and a note in place of the answer, never the half answer or its calls. The archive keeps the same, the answer marked `interrupted`: a UI reopening the conversation shows the question was left unanswered (the reads that show a conversation give it an empty text, the raw reads the note), and a conversation rebuilt from the archive gives the model the same note back. An opening stopped, or a turn stopped before it started, leaves nothing in the archive. With each answer the archive also keeps what its turn showed the person besides the text (`trace`): the reasoning, the tools' status lines and how they went, the confirmations staged, the logins asked for, up to the stop for a turn that was stopped. When a confirmation is resolved, outside any turn, the archive adds the reply the person got and how it went (`confirmation`). A UI reopening the conversation shows them as the live turn did; none of it goes back to the model, neither in a conversation rebuilt from the archive nor in `recall_verbatim`. No token and no login link is kept: a confirmation is named by a short hash of its token.

An example. Someone writes "my favourite colour is green" in a web chat and closes the tab. An hour later Mercury has freed that conversation. When they open it again and ask "what's my favourite colour?", Mercury reads the end of the conversation from the archive, puts it back in front of the model, and the answer is "green", as if no time had passed.

## What the log says about a turn

Every turn writes to the service's log (stderr) when it starts and when it ends, with how long it took, its steps and tool calls, how much reasoning and answer text the model wrote and how its generation ended (`finish stop`, for instance), or why it failed. A generation that ended on an error or at a token limit fails the turn, since its answer only looks complete. A turn still running says so every minute, with the same counts: reasoning that keeps growing with no answer is a model going round in circles. The calls to tools are logged as they happen, each with its outcome.

## Traces

Besides the log, the agent can record every turn, model step, tool call, memory decision and startup as an event (`traces` in the config, see [Traces](https://github.com/lucabro81/mercury-fw/blob/main/apps/docs/src/content/docs/concepts/traces.md)). The core is the only place an event is shaped: it cuts it to the instance's level, `meta` (names, outcomes, durations, sizes) or `args` (also the tools' input, the summary of an action waiting for confirmation, and the error messages), and replaces the person's key and the session key with pseudonyms made from a secret it generates on first start, in `trace-secret` in the data folder (`MERCURY_DATA_PATH`). The conversation's text never enters an event; each turn's events and its archived messages share a `turnId`. An event never costs a turn anything: a sink that fails is logged once and ignored.

## Who sees what

The core keeps one identity per person, `<provider>:<id>` (`google-chat:users/42`, `oidc:<sub>`), so two providers issuing the same id are still two people. Memory, the conversation archive, the tool log and pending confirmations are kept per person, and a confirmation can only be confirmed by whoever staged it.

The wiki has a common area, `curated/`, that everyone reads, and an area per person under `users/<key>/`, which the model sees as `personal/`: `personal/notes/` is what it writes for that person, `personal/inferred/` what consolidation learned about them. Nobody sees anyone else's area. The model can't write the common area directly: `promote_note` copies one of the person's notes there, and only once they confirm it with the token. The operator's tools (`mfw vault`, the nightly review) still see the whole vault.

How a person wants to be called is a setting the core keeps for them, not a note: they say it in conversation and the model saves it with `set_preferred_name`, into `profiles.json` in the data folder (`MERCURY_DATA_PATH`), out of the model's reach. From then on every one-to-one turn tells the model their name (a shared space already names each sender). A channel can ask the assistant to speak first (`opening` on the turn, with no text): it does only for someone whose name it doesn't know, introducing itself and asking, and says nothing otherwise. The HTTP surface does this right after a sign-in, and `reads.me` tells it whether the core knows the caller's name.

The language a person wants is kept the same way: they ask for one ("talk to me in Italian") and the model saves it with `set_preferred_language`, one of the languages the instance ships, offered only when it ships more than English. From then on every one-to-one turn tells the model to answer in it, and the fixed texts the core writes itself (a refusal, the account-linking replies, a confirmation's reply, the login errors, the tool status lines, the terminal's own lines) come out in it too. Those texts are English in the core; the instance adds a language with a file of its own, declared in `mercury.config.ts` under `i18n`, and whoever hasn't chosen one gets the language their client asks for when the channel passes it on (`InboundTurn.languageHint`: HTTP's `Accept-Language`, Google Chat's client language), else `i18n.defaultLocale`. The plugins' and the channels' texts work the same way, each one's English under its own name (`web-search.…`, `google-chat.…`), and so do the app's own (a formatter rule's), under `app.` in its `locales/en.json`. A key a language's file lacks shows as the key itself, never as English, and the log names the missing keys at startup, the core's, the plugins' and the app's. See [Languages](https://github.com/lucabro81/mercury-fw/blob/main/apps/docs/src/content/docs/concepts/languages.md).

Every turn reaches the model after a line saying when and where the person wrote it, `[Wednesday 2026-10-21 14:32 Europe/Rome]`, and the system prompt says what that line is: without it the model doesn't know what day it is. The line is on the model's input only, never on the text the channel sent, so the verbatim archive keeps the message as written, with its own timestamp; a resumed conversation's messages come back stamped from that timestamp. The semantic-fact extractor and the capture card's preview leave it out, while the summaries keep the dates it gives (the episodic one quotes a date only from there, never guessing). The time is in the person's time zone, an IANA name: the one they saved (they tell the model, which calls `set_time_zone`, or a channel's settings save it, `ctx.settings.setTimeZone`, the HTTP surface's `PATCH /me`), else the one their client is in when the channel passes it on (`InboundTurn.timeZoneHint`: HTTP's `X-Time-Zone`, Google Chat's client time zone), else `i18n.timeZone`, else the machine's. `reads.me` says the saved one too. A `timeZone` that isn't a zone's name stops the start.

An instance that ran an earlier version gets its data moved at startup: Google Chat and terminal notes into their areas, the memory's ids onto the new keys. An id that doesn't say which provider it came from stays where it is, with a line in the log.

## Several people at once

Different people, and different conversations of one person, run in parallel. Turns of one conversation run one after the other: a second message sent while the first is still being answered (two tabs on one chat, a double submit) waits for it, and the idle capture waits too before it closes a conversation. A vault write that depends on what's there (a consolidation, an `index.md` update, a promotion) decides inside the same queue the write goes through, so a concurrent update is never lost. The nightly review rewrites or deletes only the version of a document it read, and rereads it when someone changed it meanwhile.

The instance's `context` (`context/context.ts`): checked at startup against the plugins declared and loaded (a layer pointing at an undeclared plugin, or one with no layer, a plugin listed twice, or a budget that isn't a whole number, stops the start); the person's profile (the first in `assign` naming one of their roles, else `default`) is picked at their first turn in a session and kept until it closes, and gives the layers, run only for plugins offered to them. `session` layers are built once per session and person (each sender their own, in a shared space) and go into the system prompt after the primer, one that failed or wasn't offered then staying out until the session closes; `turn` layers are built every turn and go in front of the person's last message in the model call only. Whole blocks fill the budget, session layers first. One `context.assembled` event per turn.

A plugin's hooks (`plugins/plugin-hooks.ts`): the turn runner reports each turn that ended with an answer and the idle sweep each session it closed; the core hands them to the `afterTurn`/`onSessionClose` of the plugins offered to that person (in the session's last turn, for a close), without waiting, one `plugin.hook` event each. A plugin's `ctx.job` runs on the same queue as the core's own work, named `<plugin>:<name>`, and the turn model a plugin gets is queued too.

The work nobody waits on (titles, memory captures, corrections, the archive's index, the nightly review) runs on the `background` model, the turn's when none is declared, through the core's queue (`model/scheduler.ts`): one queue per declared model, where a turn counts on the turn model from its arrival until its answer is out and is never held back, and background work runs one model call at a time, only in the slots turns leave free of the model's `capacity`, at most `backgroundSlots` at once, `soon` work (titles, corrections, the archive's index) before `idle` (captures, the review). It runs outside the session's lock, so a conversation's next turn never waits for it. Turns themselves aren't limited: how many reach the model at once is the model server's business (on Ollama, `OLLAMA_NUM_PARALLEL`, which a model's `capacity` should match). Measure it on your own hardware before counting on it: on one setup, a follow-up that took 5 seconds for one person took about two minutes with two people talking at once.
